# MADAR 4.0 · Admin and React developer guide

The React application lives in `apps/admin`. Production serves its built files from the Express service. The browser preview in `demo/MADAR_Offline_Preview.html` uses local sample data and visibly labels that mode; it does not connect real TVs.

## Operator workflow

1. Sign in, then maintain **Master Data**: buildings, locations, departments, device groups, rooms, service counters, categories, languages and media providers. Use the relevant display profile and screen-management pages for profiles, themes, registered devices and schedules.
2. Open a content section. **Add item** opens a form driven by `/api/admin/catalog`. Enter English/Arabic text, category, audience, owner, dates and the fields relevant to that section. Master selectors link rooms, counters and locations. Category and department selectors use their managed names.
3. Upload image artwork in the side panel. PDF attachments, MP4 videos and MP3 audio have their own file controls where applicable. Image uploads become verified WebP assets. Other uploads require malware scanning in production. The API rejects unsupported files and external artwork in a published release.
4. Save **draft**, submit for **review**, or publish as an administrator. Editor roles cannot publish. Draft edits do not replace an existing published snapshot. Each edit uses a revision guard to prevent overwriting another operator's changes.
5. Open **Content Fields** to add typed fields to any of the 14 content collections. Supported types: text, long text, number, boolean, date, HTTPS URL and selection. Field keys are stable. Labels can be bilingual. Required fields and select choices are validated server-side. Make new fields optional until existing records are populated. Definitions incompatible with stored records are rejected.
6. **Show on TV** places a custom field in the details view. Turning it off excludes the value and field definition from device releases. Fixed security, media and publishing fields remain system controlled. New executable widget types require code changes in both clients; administrators cannot upload executable widgets.
7. Use **Page Builder** to choose and order widgets and **Dashboard Designer** for operational grid positions. Configure titles, limits, categories, styles and supported refresh/rotation settings. Publish the selected profile. Layout rollback restores a draft that must be reviewed and published again.
8. Install the TV app, request pairing, and approve its code under **Screens & Devices**. Assign the profile, initial page, group and location. The device receives only its permitted published experience. Automatic discovery creates a pending enrollment, never automatic permission to see internal content.
9. Check **Screen Delivery**. Received means receipt, Downloaded means verification, and Applied means the player reports it rendered the release. The server does not fabricate Applied for offline screens.

## Bulk JSON import

Each content list accepts a JSON array of 1–100 records, under the API body limit. Imports are atomic: one invalid item rejects the batch. Imported IDs are generated by the API; imports create records rather than overwriting by title. Referenced content and masters must already exist. For example:

```json
[
  {
    "title": "Visitor parking guidance",
    "titleAr": "إرشادات مواقف الزوار",
    "description": "Use the visitor spaces beside the main reception.",
    "category": "Information",
    "status": "draft",
    "visibleTo": ["public", "employee", "management", "vip", "signage"],
    "sortOrder": 10,
    "owner": "Visitor Services",
    "building": "MADAR Campus",
    "floor": "Ground floor",
    "openingHours": "07:30–14:30",
    "accessibility": "Step-free access from the east entrance"
  }
]
```

Select **Visitor Guide** for this example. Custom fields go inside `customFields`, after defining them in Content Fields.

## Master lists

| Master | Purpose and fields |
|---|---|
| Buildings | Name, Arabic name, address, description, active, order |
| Locations | Name, building, floor, directions, accessibility, active, order |
| Departments | Name, contact, service hours, active, order |
| Device groups | Name, purpose, active, order; the matching group name is used in screen scheduling |
| Rooms | Name, location reference, capacity, available/occupied/unavailable |
| Counters | Name, location reference, service, available/serving/paused/closed |
| Categories | Name and content collection; used in content filters and TV category controls |
| Languages | Code, name, text direction; metadata registry, not an automatic translation system |
| Providers | Name, protocol, server-side reference prefix and support contact; credentials stay in server configuration |

Standard TV interface localization is English/Arabic. Additional language metadata does not implement new interface translations. Master deletion is blocked when content, screens, schedules or other masters still reference it. Name/code-based references must be updated before renaming an in-use value; ID-based links preserve identity. Deactivation retains history. Master changes publish fresh device releases. Room and counter data can be manually maintained or supplied by authenticated external feeds.

## Dashboard and reports

The **Control Room** shows real registered/online/offline/synced counts, content totals, review counts, publication activity, latest delivery stages and screen locations. A newly seeded environment correctly shows offline, unconfirmed demo TVs. No fake operational success is displayed.

Reports cover **Device health**, **Delivery acknowledgements**, **Content inventory**, **Publishing activity**, and **Saved content**. Search and status filters apply where relevant; device and delivery reports also filter by profile. Date filters are UTC; device health is a current snapshot, not historical uptime. CSV values are quoted and spreadsheet formula prefixes are escaped. Reports cap source rows at 5,000 and flag truncation; narrow dates for complete large exports. Publishing audit details require an administrator. Favourites show saved-item counts, not viewing duration or audience analytics.

## React development

```sh
npm ci
npm run typecheck
npm run build
node --env-file=.env services/api/src/server.mjs
# In a second terminal, from the repository root:
npm run dev -w apps/admin
```

From `apps/admin`, `npm run dev` starts the Vite development UI with its API proxy. Start the backend separately. Keep `VITE_SHOWCASE` unset for API integration; `1` selects the clearly labelled offline adapter.

Key files: `src/App.tsx` navigation; `api.ts` API wrapper; `pages/ControlRoom.tsx`; `Masters.tsx`; `ContentFields.tsx`; `ContentManager.tsx`; `Reports.tsx`; `components/TVExperience.tsx`; `control.css`. TanStack Query manages fetch/cache invalidation. React Hook Form/RJSF drives typed content forms; dnd-kit and React Grid Layout provide layout editing. The default muted bronze is **#6B5837**, sampled from the supplied textured reference. The original logo file is retained; UI tinting uses the bronze palette. Profile theme colours can still be edited and published.

To add a content collection, register its schema/resource metadata in `domain.mjs`, connect a registered widget source, add navigation and seed records, and update API and Flutter tests. To add a new field to an existing collection, prefer Content Fields.
